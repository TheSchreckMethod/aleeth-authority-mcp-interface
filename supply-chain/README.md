# Supply chain: what we can prove about our dependencies, and what we cannot yet

Every file in this directory is generated by a script from the private
implementation repository and committed verbatim. Nothing here is hand-edited.
`provenance.json` records the tool versions, the lockfile digest and its
implementation-repo commit, and the SHA-256 of each artifact, so a reader can
detect any tampering with this directory itself.

## What is here

| File | What it is | How it is produced |
|---|---|---|
| `sbom.cdx.json` | CycloneDX 1.5 software bill of materials for the runtime dependency set | `uv export --format cyclonedx1.5 --no-dev` against the committed `uv.lock` |
| `osv-scan.json` | Vulnerability scan of the full lockfile, dev dependencies included | `osv-scanner` against the same `uv.lock`, result published verbatim |
| `provenance.json` | Generation record: tool versions, lockfile digest and commit, artifact digests | the export script, at generation time |

The SBOM covers the runtime set only, because dev tools never ship in the
image. The vulnerability scan deliberately covers the wider set, dev included,
because a compromised dev tool is still our problem to disposition.

## Current scan result

See `osv-scan.json` and the `results` block of `provenance.json` for the
authoritative numbers and date. If the scan reports findings, each one gets a
written disposition here: fixed, not applicable with the reason, or accepted
with the reason. An empty findings list is published only when the scan
genuinely returned empty.

## The lockfile and the deployed image

The lockfile is the resolved dependency set the implementation is developed
and tested against. The production image is currently built from the project's
declared dependency ranges, not directly from this lockfile. Image-from-lockfile
builds are scheduled for the next deployment; this paragraph will be removed
when that is true and not before.

## What we do not claim

We make no SLSA claim at any level. SLSA requires provenance attestations
generated by a hardened build service. Our CI is currently not running because
of an organization billing ceiling, stated plainly, so no build attestation we
could publish today would be honest. When CI is funded and running, we will
publish signed build attestations and update this document. Until then, the
absence of the claim is the claim.

The container image records honest build metadata, the git commit the platform
reports at build time, labeled as traceability. Traceability is not attestation
and we do not present it as one.
